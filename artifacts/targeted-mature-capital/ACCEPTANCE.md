## 4. 唯一优先经济假设：成熟持仓的增量资本

现有系统已有 `add_mature_leaders`、ADD1/ADD2、赢家保留及风险恢复。不要再增加平行加仓模块。

重点追踪实际调用链：

`ProductionEngine.decide → PortfolioAllocator.allocate → _allocate_strategy → _admit_new_cores / add_mature_leaders → AllocationBook.fund → Target / Order / Fill`。

重点代码：`uquant/portfolio/leaders/cycle.py`、`uquant/portfolio/pipeline.py`、`uquant/portfolio/allocation_book.py`、现行恢复与真实持仓归属路径。

需要核查的具体假设，不能预先称为bug：

1. `_pyramid_candidate` 对既有成熟持仓要求 `entry.block == READY`，是否重复依赖首次入场条件，阻断了当时具备独立增量依据的持仓？新增资本仍需当前证据，不能把“已持有”解释为永久加仓许可。
2. `_pyramid_open` 的全账户 pending-order 否决及普通修复资本状态，是否在共同账本已正确计入真实责任后仍过度阻止无冲突增量？不能删除必要的结算、迟到成交和冻结保护。
3. 新普通准入先于成熟持仓加仓，且加仓按证券代码遍历，是否使资金被经济优先级较低的请求占用？代码排序只是线索；必须记录真实资金竞争，不能假定改为分数排序必然更好。
4. `owned`/`anchor_weights` 等排除与恢复/战略所有者是否职责完整？已有路径能处理就复用，不绕过原身份，也不借普通加仓扩大旧grant授权。

先利用已有逐日数据形成一个紧凑的组合级事件表：资格、原目标、实仓、现金、BUY承诺、当前总仓/集中度余量、实际阻止原因、下一开盘可执行量、后续全部组合净损益和避免的损失。观察全部相关事件，不只选历史赢家。事后收益仅用于评估，不进入当日信号或请求排序。

至少在两个预先指定的薄弱池看到真实阻塞和有意义的资金余量，且问题未被现有路径处理，才实施经济候选。没有证据就否决这个假设，不为交付硬造机制。

## 6. 本轮建议采用的晋级合同
