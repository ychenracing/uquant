# uquant 架构说明

## 设计目标

uquant 把收盘后的市场判断、组合构建和下一交易日执行建模放在一条可审计路径中。系统优先保证因果性、状态连续性、风险权限单一和账户可恢复性。

## 决策链

```text
点时行情
  → 因果特征
  → 领涨评分
  → 机会状态 + 风险状态
  → 唯一目标组合
  → 次日开盘订单意图
  → 模拟成交或券商成交对账
  → 账户状态与日报
```

`ProductionEngine` 是编排入口。`daily` 与 `backtest` 都调用同一个 `decide()`，因此回放不能绕过生产组合规则，日报也不能自行修改目标。

## 组件职责

### 数据层

`DataStore` 负责：

- 统一证券代码；
- 校验 OHLCV、日期顺序和数值范围；
- 按决策日期截断数据；
- 计算可追加的前缀哈希；
- 为账户建立数据清单。

前缀哈希只覆盖账户上次成功运行日期以前的数据。正常追加新交易日不会使账户失效，修改已使用的历史行会触发拒绝运行。

### 特征与领涨层

`features.py` 只使用当前行和历史行生成 ATR、收益率、均线、突破、波动、量能、趋势斜率、动量加速度和回撤特征。

`industry.py` 先在评审后的稳定参考篮子中按行业汇总 20/60/120 日中位收益、均线广度和动量加速度。成员不足的行业会把分数收缩到中性，避免一只极端股票代表整个行业。

`leader.py` 令生产 `REFERENCE_UNIVERSE` 恒等于 `STABLE_REFERENCE_UNIVERSE`，在该篮子上计算截面位置，再结合相对强弱、趋势完整度、突破、韧性、量能、历史长度和行业证据形成 `LeaderScore`。`EXPANDING_RESEARCH_REFERENCE` 只进入离线 `RESEARCH_REFERENCE_UNIVERSE`，不会改变生产百分位、广度、缓存键或数据要求；晋级必须显式修改稳定篮子。成熟与新兴标记需要连续确认，不能由单日跳变直接获得生产权重。已知证券使用评审映射；未映射证券只允许用当时可见收益相关性推断行业，并携带推断置信度。行业证据参与评分、admission、handoff 和 scout 确认，但不拥有仓位。

长期 `secular_score`、证据置信度和行业分散同时用于两个独立的动态发现流程：组合层从用户全集发现且每个 epoch 都必须凑齐 3 只战略证券（至少 241 个可见收盘、默认 `secular_score >= 0.58`、长期置信度不低于 0.65、证券 20 日收益不低于 -5%、行业推断可信、科技指数 120 日收益不高于 20%、签名连续 2 日）；风险层从稳定参考篮子确认最多 3 个跨行业风险锚。`secular_score` 是跨截面长期证据，不再叠加 240 日绝对收益线，短周期反弹也不能 bootstrap 首个 epoch。候选签名、路线和确认 streak 都写入账户，回放不会因为临时改变输入顺序而改写过去的选择。

### 双轴状态

机会轴由 `opportunity.py` 管理，描述市场是否值得承担风险；风险轴由 `risk.py` 管理，决定最多允许承担多少风险。两者独立计算：强机会不能覆盖危机仓位上限，低风险也不能凭空制造买入机会。

风险层不只使用离散票数。它把 MA20/MA60 广度、广度下降、领涨失效、相关性、波动和持仓压力合成为连续 `transition_damage` 与 `trend_health`，并把连续转坏、震荡/弱势中的慢性退化和资本回撤分别持久化。风险执行分为三级：level 1 冻结新增风险；level 2 在冻结基础上施加总仓上限；level 3 进入危机级减仓。修复必须满足连续低损伤天数，不能由单日反弹跳级恢复。

`risk_sector.py` 观察实际持仓，而不是用整个参考篮子稀释窄行业风险。只有重复出现同步单日下跌，并且科技相对宽基的长期偏离足够大时，状态才进入 Level-2 并把总仓限制为 82%；它会持久化触发时的经济 cohort，确保稀疏减仓后仍有完整恢复观察集。恢复必须满足最短保护期、正收益、均线修复广度和连续确认。它只向 `risk.py` 返回证据，仓位上限仍只有一个写入者。组合层把这类减仓标记为 `sector_guard`，与 `risk_off`、`crisis` 和 `capital_budget` 保持结构化归因边界。

### 组合层

`PortfolioAllocator` 是目标权重的唯一所有者。它负责：

- 根据机会和风险确定目标总仓位；
- 在普通领涨路径完成 scout 后，对 `CHOPPY`/`WEAK` 分别施加 60%/25% 的新增机会预算，并稀疏取消弱证据增量；已有 Core 的强制减仓仍由确认风险或自身生命周期负责；
- 根据领涨数量动态调整持仓数；
- 管理 CORE、ADD1、ADD2、SATELLITE、RECOVERY 生命周期；
- 发现动态战略 cohort；成熟路线优先采用独立合格的同产业同步组，否则回退到全市场相对排名；完整退出和 30 个可见交易日冷却后，原成员或满足变化门的新成员都必须凭新的连续证据开启下一 epoch；
- 区分最终的战略 ATR/灾难退出与可恢复的风险压缩；后者只有健康确认后才按保存比例恢复，逐票达到目标且不存在待成交 BUY 后才清除 restore 状态，并继续受风险上限约束；
- 仅在双指数长期弱势，或一弱一稳且分化充分的空仓修复路线中，把单票战术探针限制为 60%；过渡路线只接纳可晋升的深跌候选，并只对已获得 20% 峰值 MFE 的恢复赢家启用 10% 峰值回撤 trail；
- 执行最短持有、替换确认、轮动频率和目标迟滞；
- 在高置信强趋势中把初始仓位提高到受风控限制的 90%/95%；只有韧性、相对强度、流动性和票间相关性联合证据同时达标才按 conviction 不等权，否则保持等权；
- 只在行业 hand-off、新兴分数、空槽、确认期和闲置现金共同成立时，由同一组合建立默认最多 6% 的跨行业 challenger scout，不为探针卖出现有核心；
- 管理冲击后的恢复锚点与资本保护；
- 在任何风险仓位上限下，以生命周期损伤为绝对优先级做确定性有限搜索，只在结构等价时最大化不变目标，至多保留一个边界裁剪且禁止加仓；
- 强制总仓、单票、持仓数和行业集中度上限。

其他模块只能提供证据或执行结果，不能直接提交目标权重。

实现按职责拆分但没有增加第二个组合：`portfolio_core.py` 保存硬约束和共享状态操作，`portfolio_strategic.py` 管理长周期组合，`portfolio_leaders.py` 管理动态 K、行业确认与普通轮动，`portfolio_recovery.py` 管理恢复锚点替换，`portfolio.py` 负责唯一编排出口。分层类最终只组合成一个 `PortfolioAllocator`。

### 执行层

`ExecutionPlanner` 把最终目标变成次日开盘意图，并统一处理：

- 信号日不得成交；
- 停牌和无成交量；
- 一字涨跌停；
- 100 股手数与科创板首次 200 股；
- T+1 可卖数量；
- 成交量参与率；
- 佣金、印花税、过户费与滑点；
- 现金、单票和持仓数量上限；
- 阻塞订单、部分成交、取消和替换。

订单生命周期存入 `AccountState.order_ledger`。同一意图持续存在时复用原 `order_id`，避免每日重复计数。普通策略退出维持 FIFO；风险减仓携带 `RISK_PRIORITY`，按 SATELLITE、ADD2、ADD1、RECOVERY、CORE 顺序卖出可卖 tranche，进入 CORE 后再优先处理 MAE 更深、MFE 更小、入场证据更弱的 lot。

### 账户与券商对账

`account.py` 使用临时文件、刷盘和原子替换保存 JSON。当前 schema v3 除现金和订单外，还保存 tranche 入场证据、订单/成交减仓策略、战略 cohort 与 epoch、动态风险锚候选、连续风险信号、慢性退化、资本预算和 scout 状态。加载时校验 schema 版本、现金、订单序号、状态、挂单引用、成交引用和唯一标识。旧 schema 默认拒绝加载，只有显式确认代码变化的 `account-migrate` 可以迁移，并记录新旧 schema、代码指纹和 UTC 时间。

`broker.py` 把券商快照视为以下字段的权威来源：

- 现金；
- 持仓股数与成本；
- 当日可卖股数；
- 已成交订单。

策略的机会、风险、迟滞、持仓/lot 生命周期和历史最高收盘状态继续保留，券商持仓字段不能回写这些状态。由系统订单成交形成的新 lot 使用订单生命周期和真实成交价格；无法由订单或已有 lot 解释的外部库存使用显式降级默认，并写入对账审计。

成交数组没有时间语义。跨日成交按 ISO 日期排序；同日多笔新成交必须提供唯一 `execution_sequence`，系统先确定顺序，再验证每个订单的部分成交、剩余量和最终成交转换。`final` 与 `remaining_shares` 均为必填字段，缺失或矛盾时整份快照原子失败。重复 `fill_id` 只有在经济字段完全相同时才保持幂等，未知 `order_id`、证券/方向不一致或终态订单新增成交都会被拒绝。

## 状态所有权

| 状态 | 唯一所有者 |
|---|---|
| 行情截断与数据指纹 | `DataStore` |
| 机会状态 | `classify_opportunity` |
| 风险状态和仓位上限 | `assess_risk` |
| 动态风险锚、连续损伤与资本预算 | `assess_risk`，状态存入 `AccountState` |
| 持仓同步冲击状态 | `risk_sector.update_sector_guard`，最终权限仍归 `assess_risk` |
| 动态战略 epoch、目标权重与持仓生命周期 | `PortfolioAllocator` |
| 订单与成交状态 | `ExecutionPlanner` / `sync_broker_snapshot` |
| 持久化 | `account.py` |
| 展示 | `report.py` |

## 关键不变量

1. 每只证券每天最多一个最终目标和一个方向。
2. 所有买卖必须来自最终目标与当前账户之间的差异。
3. 总目标权重不超过 `max_gross`，单票不超过 `max_symbol_weight`。
4. 目标持仓数不超过 `max_positions`。
5. 风险模块是仓位上限的唯一写入者。
6. 决策日数据不能在决策日开盘成交。
7. 实际成交必须能追溯到稳定订单标识。
8. 数据或代码身份不一致时不静默继续。
9. 账户 schema 不匹配时必须显式迁移并留下审计记录。

## 发布验证边界

`uquant.validation.manifest` 对冻结 CSV、`DATA_MANIFEST.json` 和 `SHA256SUMS` 做三方清单及 SHA-256 校验，并拒绝符号链接和不安全文件名。`uquant.validation.promotion` 使用版本化股票池、窗口和财富/回撤/订单/换手门槛执行回归矩阵。

`uquant.validation.generalization` 构造 remove-one/pairs/all、no-optical、行业单池/平衡池、确定性 random 6/12/24 和只用窗口前证据的 leave-top-k，输出 PDI、行业 PnL 占比以及财富/回撤/订单分位数。`uquant.validation.competitor` 要求 5 池 × 7 窗口 × 3 项目的 105 个真实单元，并锁定 commit、adapter、数据和统一执行契约。两者只读取评审 reference，不提供 baseline 写入 API；缺失、不完整或漂移即 fail closed。GitHub Actions 将类型、覆盖率、构建、安全审计和策略晋级分成独立门，策略改动不能靠普通单元测试绕过绩效门。

仓库根目录的 `research/` 提供共享参数候选搜索、dominance/Pareto 比较、单能力消融、参数与股票池压力、以及成交后退出归因的离线 Python primitives。它没有生产 CLI，不构造或导入 `ProductionEngine`，且任何 `uquant` 模块都不导入它；调用方必须显式提供回放观测或回调。研究结果只有经过上述生产晋级门和 reference 评审后，才能成为稳定配置或稳定参考篮子变更。

## 扩展边界

新增数据源应实现与 `DataStore` 相同的字段、复权和点时约定；新增机会证据应进入机会分类器；新增风险证据应进入风险模块；新增持仓规则应进入组合分配器；新增市场微观约束应进入执行层。不要在 CLI、日报或券商对账模块中复制策略判断。
