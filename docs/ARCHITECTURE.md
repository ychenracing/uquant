# uquant 架构说明

## 设计目标

uquant 把收盘后的市场判断、组合构建和下一交易日执行建模放在一条可审计路径中。系统优先保证因果性、状态连续性、风险权限单一和账户可恢复性。

## 决策链

```text
点时行情
  → 因果特征
  → 领涨评分
  → 机会状态 + 风险状态
  → 唯一目标组合
  → 次日开盘订单意图
  → 模拟成交或券商成交对账
  → 账户状态与日报
```

`ProductionEngine` 是编排入口。`daily` 与 `backtest` 都调用同一个 `decide()`，因此回放不能绕过生产组合规则，日报也不能自行修改目标。

## 组件职责

### 数据层

`DataStore` 负责：

- 统一证券代码；
- 校验 OHLCV、日期顺序和数值范围；
- 按决策日期截断数据；
- 计算可追加的前缀哈希；
- 为账户建立数据清单。

前缀哈希只覆盖账户上次成功运行日期以前的数据。正常追加新交易日不会使账户失效，修改已使用的历史行会触发拒绝运行。

### 特征与领涨层

`features.py` 只使用当前行和历史行生成 ATR、收益率、均线、突破、波动、量能、趋势斜率、动量加速度和回撤特征。

`industry.py` 先在固定参考篮子中按行业汇总 20/60/120 日中位收益、均线广度和动量加速度。成员不足的行业会把分数收缩到中性，避免一只极端股票代表整个行业。

`leader.py` 在同一参考篮子上计算截面位置，再结合相对强弱、趋势完整度、突破、韧性、量能、历史长度和行业证据形成 `LeaderScore`。成熟与新兴标记需要连续确认，不能由单日跳变直接获得生产权重。行业证据只提供确认，不拥有仓位。

### 双轴状态

机会轴由 `opportunity.py` 管理，描述市场是否值得承担风险；风险轴由 `risk.py` 管理，决定最多允许承担多少风险。两者独立计算：强机会不能覆盖危机仓位上限，低风险也不能凭空制造买入机会。

`risk_sector.py` 观察实际持仓，而不是用整个参考篮子稀释窄行业风险。只有重复出现同步单日下跌，并且科技相对宽基的长期偏离足够大时，状态才激活；恢复必须满足最短保护期、正收益、均线修复广度和连续确认。它只向 `risk.py` 返回证据，仓位上限仍只有一个写入者。

### 组合层

`PortfolioAllocator` 是目标权重的唯一所有者。它负责：

- 根据机会和风险确定目标总仓位；
- 根据领涨数量动态调整持仓数；
- 管理 CORE、ADD1、ADD2、SATELLITE、RECOVERY 生命周期；
- 执行最短持有、替换确认、轮动频率和目标迟滞；
- 管理冲击后的恢复锚点与资本保护；
- 在持仓同步冲击上限下，以确定性有限搜索减少不必要的目标变化且禁止加仓；
- 强制总仓、单票、持仓数和行业集中度上限。

其他模块只能提供证据或执行结果，不能直接提交目标权重。

实现按职责拆分但没有增加第二个组合：`portfolio_core.py` 保存硬约束和共享状态操作，`portfolio_strategic.py` 管理长周期组合，`portfolio_leaders.py` 管理动态 K、行业确认与普通轮动，`portfolio_recovery.py` 管理恢复锚点替换，`portfolio.py` 负责唯一编排出口。分层类最终只组合成一个 `PortfolioAllocator`。

### 执行层

`ExecutionPlanner` 把最终目标变成次日开盘意图，并统一处理：

- 信号日不得成交；
- 停牌和无成交量；
- 一字涨跌停；
- 100 股手数与科创板首次 200 股；
- T+1 可卖数量；
- 成交量参与率；
- 佣金、印花税、过户费与滑点；
- 现金、单票和持仓数量上限；
- 阻塞订单、部分成交、取消和替换。

订单生命周期存入 `AccountState.order_ledger`。同一意图持续存在时复用原 `order_id`，避免每日重复计数。

### 账户与券商对账

`account.py` 使用临时文件、刷盘和原子替换保存 JSON。加载时校验 schema 版本、现金、订单序号、状态、挂单引用、成交引用和唯一标识。旧 schema 默认拒绝加载，只有显式确认代码变化的 `account-migrate` 可以迁移，并记录新旧 schema、代码指纹和 UTC 时间。

`broker.py` 把券商快照视为以下字段的权威来源：

- 现金；
- 持仓股数与成本；
- 当日可卖股数；
- 已成交订单。

策略的机会、风险、迟滞和生命周期状态继续保留。重复 `fill_id` 会被忽略，未知 `order_id` 或证券/方向不一致会被拒绝。

## 状态所有权

| 状态 | 唯一所有者 |
|---|---|
| 行情截断与数据指纹 | `DataStore` |
| 机会状态 | `classify_opportunity` |
| 风险状态和仓位上限 | `assess_risk` |
| 持仓同步冲击状态 | `risk_sector.update_sector_guard`，最终权限仍归 `assess_risk` |
| 目标权重与持仓生命周期 | `PortfolioAllocator` |
| 订单与成交状态 | `ExecutionPlanner` / `sync_broker_snapshot` |
| 持久化 | `account.py` |
| 展示 | `report.py` |

## 关键不变量

1. 每只证券每天最多一个最终目标和一个方向。
2. 所有买卖必须来自最终目标与当前账户之间的差异。
3. 总目标权重不超过 `max_gross`，单票不超过 `max_symbol_weight`。
4. 目标持仓数不超过 `max_positions`。
5. 风险模块是仓位上限的唯一写入者。
6. 决策日数据不能在决策日开盘成交。
7. 实际成交必须能追溯到稳定订单标识。
8. 数据或代码身份不一致时不静默继续。
9. 账户 schema 不匹配时必须显式迁移并留下审计记录。

## 发布验证边界

`uquant.validation.manifest` 对冻结 CSV、`DATA_MANIFEST.json` 和 `SHA256SUMS` 做三方清单及 SHA-256 校验，并拒绝符号链接和不安全文件名。`uquant.validation.promotion` 使用版本化股票池、窗口和财富/回撤/订单/换手门槛执行回归矩阵。GitHub Actions 将类型、覆盖率、构建、安全审计和策略晋级分成独立门，策略改动不能靠普通单元测试绕过绩效门。

## 扩展边界

新增数据源应实现与 `DataStore` 相同的字段、复权和点时约定；新增机会证据应进入机会分类器；新增风险证据应进入风险模块；新增持仓规则应进入组合分配器；新增市场微观约束应进入执行层。不要在 CLI、日报或券商对账模块中复制策略判断。
