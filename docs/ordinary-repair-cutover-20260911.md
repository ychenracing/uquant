原生回放来自冻结的独立生产目录，交付目录通过完整生产源码指纹确认一致；原始运行提交身份保留，不改写成交付提交。

## 行为变化

- 真实资金修复完成后，普通成熟股可以按原有确认和风险上限入场。
- 已修复持仓仍在时，当前独立组合、双股或单股资格允许新增普通持仓；这些新增持仓和未成交委托共享已有的 20% 基础额度。
- 原修复持仓须由真实消费的 order/event、成交和剩余批次共同证明，才能与新增额度分开核算。旧账户缺少来源标记时不猜补，也不获得来源豁免。
- 当普通持仓与未成交额度仍超过基础额度时，后续买单必须保持当前独立资格。降回基础额度内后，仍须通过当前普通入场资格和全部风控。
- 同步恢复已有持仓也必须满足现有票数、风险档位和市场损伤修复条件。

上述改动不产生战略 grant/epoch 所有权，不改变费用模拟、实际订单身份或风险卖出权限。
没有新增配置参数、服务、数据源或账户顶层 schema；状态沿用现有计数字段与原生订单/成交引用。
本次聚焦审查未发现重要的资金权限或订单身份问题；它不替代经济回放。

## 切换

1. 按 `OPERATIONS.md` 保留完整账户、成交、在途订单和数据的独立备份，在副本上操作。
2. 使用选定发布源码和锁定依赖，核对 schema 8、账户身份、数据前缀及持仓证券。研究使用的冻结环境是 Python 3.12.13、NumPy 2.5.1、pandas 3.0.5、uv 0.11.33。
3. 代码身份不一致时，使用已有 `account-code-migrate` 流程；核对迁移前后经济状态摘要一致。该操作不重置现金、股数、成本、资本峰值、订单序号、授权或确认计数。
4. 不手工添加 `ordinary_repair_origin:*` 标记，不从旧持仓反推新修复权限。缺少历史证明的资本继续受基础额度约束，后续由真实观察和成交建立证明。
5. 切换前核对全部未成交买卖单。已有成交不能因升级、撤销余单或回滚而消失；回滚必须先对账，不能直接用过期备份覆盖后续成交。

本轮只进行历史回放与代码交付，不执行真实账户迁移、券商操作或实盘下单。
2026-08-06 起的 Future Holdout 不参与历史选择，也不回填。
