# uquant 改造方案：消除评估偏差、过拟合、复杂度、数据与执行问题

> 状态：提案，尚未实施。本文不改变当前生产行为，也不构成新的经济验收结论。
> 范围：前瞻验证（Future Holdout）与单票集中风险按用户决定**不在本方案范围内**。

## 0. 结论先行

本方案覆盖六类问题，按根因归并为四条工作线，并规定了执行顺序：

| 编号 | 问题 | 根因 | 能否"完全消除" |
|---|---|---|---|
| P1 | 股票池事后挑选（幸存者/赢家偏差） | 成员名单在 2026-08 统一审定，全部从上市日起生效、无一退出 | **成员偏差可以完全消除**（改为规则化的点时股票池）；**主题选择偏差**（在 2026 年才知道 AI 是主线）任何代码都消除不了，只能用跨主题检验把它变成可度量的风险 |
| P2 | 验收门槛锚定历史暴利 | 15 倍财富底线、冠军 23.28 倍 / 24.5 倍的 95% 等绝对门槛 | **可以完全消除**（改为预先登记的相对基准门槛） |
| P3 | 规则堆叠带来的过拟合 | 254 个固定参数、手工权重评分、24 种经济机制、85 个持久化账户字段，全部在同一段 2023–2026 样本上迭代 | 不可能降到零；**可以变成"可度量、有上限"**：参数预算、试验台账、PBO/DSR 统计、跨主题验证集 |
| P4 | 工程复杂度远超需求 | 生产包 7.3 万行，其中验证治理 3.07 万行；回测每个决策日约 0.78 秒；CI 每次推送消耗数小时 | **可以完全消除**（v2 精简内核加上独立的评估实验室） |
| P5 | 日常数据链路不通 | 前复权数据与"只追加 + 历史前缀哈希"机制冲突；CLI 没有刷新命令；指数无法刷新；只校验哈希、不校验内容 | **可以完全消除**（原始价格加复权因子分开存储，加每日刷新和内容校验） |
| P6 | 执行模型瑕疵与人工交易摩擦 | 涨跌停只按代码前缀判断；印花税不随日期变化；按前复权价算股数却按原始成交量算容量；送转和人工成交导致同步失败 | **可以完全消除** |

最关键的执行顺序：**先修数据（P5/P6），再建评估实验室（P1/P2），用新实验室诊断现有策略，最后在实验室约束下重建精简内核（P3/P4）。** 如果先做精简，就没有可信的尺子判断哪些模块该留。

## 1. 现状证据（本方案的出发点）

以下数字都在 `main` 分支提交 `d6eaa7d` 上用 `data/frozen` 实测，或直接读取仓库代码得到。

### 1.1 收益来源高度集中在一只股票上

| 场景 | 策略终值 | 最大回撤 | 订单数 | 同池等权买入持有 |
|---|---:|---:|---:|---:|
| 34 只全池，2023-01-03 起 | 23.61 倍 | 26.6% | 33 | 9.94 倍 / 42.3% |
| 起点 2023-02-01 | 23.94 倍 | 30.4% | 26 | — |
| 起点 2023-03-01 | 12.74 倍 | 27.1% | 75 | — |
| 起点 2023-07-03 | 12.18 倍 | 26.1% | 79 | — |
| 剔除 sz300308（中际旭创） | 2.88 倍 | 27.9% | 100 | 8.47 倍 / 43.0% |

- 全池 33 笔订单中有 23 笔是 sz300308。第一笔在回测第二个交易日（2023-01-04），市场状态为 `CHOPPY`，目标权重 95%。当日该股 120 日收益为 −6%，250 日收益为 −35%。
- 起点只挪一个月，终值就从 23.9 倍掉到 12.7 倍，说明结果对路径极度敏感。

### 1.2 股票池与门槛

- `uquant/contracts/resources/ai_universe_manifest.json`：34 只成员的 `effective_from` 等于各自上市日，`effective_to` 全部为 `null`，`reviewed_at` 全部为 `2026-08-14`。
- `uquant/validation/acceptance_tolerance.py`：`principal_wealth_floor()` 返回 `15.0`；`benchmarks/cross_ai_core_strategy_contract.json` 要求 5 标的和完整池 ≥ 23.284 倍；Ownership 合同要求保留冻结冠军 24.51 倍的 95%。

### 1.3 复杂度

| 维度 | 现状 |
|---|---|
| 生产包 `uquant/` | 73,121 行；其中 `validation/` 30,704 行，`portfolio/` 12,005 行 |
| 测试 / 研究 | 115,224 行 / 27,518 行 |
| 固定规则参数 | `uquant/config/policies.py` 中 254 个 `ClassVar`，另有评分内的手工权重（例如 `leader.py` 中的 `0.23*momentum60 + 0.12*momentum120 + …`） |
| 经济机制 | `AttributionMechanism` 共 24 种可产生交易的机制 |
| 账户状态 | `AccountState` 85 个持久字段 |
| 回测速度 | 34 只股票每个决策日约 0.78 秒，全区间约 5 分钟。剖析显示 `strategic_qualification_snapshots` 约占 34%，`compute_structural_leaders` 每天重复调用 2 次以上，`_inferred_industries` 每天重算，大量逐日 `pandas .loc` 在完整历史上切片 |
| CI | 测试矩阵墙钟约 47 分钟；Absolute 8 个分片墙钟约 88 分钟，单次推送消耗数个 runner 小时 |

### 1.4 数据与执行

- `uquant/application/decision.py:318-329`：账户保存全部证券历史前缀的哈希，历史被改写就抛出 `historical data prefix differs from account state`。前复权数据在每次分红或送转时都会改写该股全部历史，两者从根本上冲突。
- `uquant/data.py:232`：`refresh_akshare` 没有接入 CLI，指数刷新会被直接拒绝。
- `sz000636` 缺少 2022-01 到 2023-12 的全部数据，`DATA_MANIFEST` 校验照样通过。
- 2023 年以后有 1,946 行（约 6%）缺少 `amount`，改用"前复权收盘价 × 成交量"估算，结果偏低。
- 单位错配：`sz300308` 在 2023-01-03 的前复权收盘价为 17.97，而成交额 ÷ 成交量得到的真实均价约为 27.85。`open_execution.py:276` 按前复权价计算股数，`open_execution.py:231-238` 却按原始成交股数计算 0.5% 参与率容量，并用"隐含值大于 50 倍就乘以 100"的启发式猜测单位。
- `market_constraints.py:14-16`：涨跌停只看代码前缀是否为 `300`/`688`，因此 `301`、ST、北交所、新股前 5 日都会判错。
- `fees.py` 与 `config/model.py`：印花税固定 0.05%（2023-08-28 之前实际为 0.1%）。
- `broker.py:784-785`：券商持仓股数大于系统已知买入数量（例如送转后）时抛出 `exceeds known BUY lot inventory`。`broker.py:387`：不是系统订单产生的成交会被拒绝。`broker.py:812-813`：券商持仓超过 6 只直接报错。

## 2. 总体路线

```
阶段 0  冻结 v1、登记方案 ────────────────────────────────┐
阶段 1  数据层重建（P5）                                   │ v1 继续每日使用，
阶段 2  执行模型修正（P6）                                 │ 只接受运维类桥接修复
阶段 3  评估实验室：点时股票池、基准、指标、跨主题面板（P1） │
阶段 4  用实验室诊断 v1 ──► 决策点 D1                      │
阶段 5  v2 精简内核：从简单基线出发，逐模块准入（P3、P4）   │
阶段 6  新门槛与 CI（P2）                                  │
阶段 7  影子并行 ──► 切换 ──► 清理 v1 ───────────────────────┘
```

原则：

1. **保留现有优势**：严格因果（收盘决策、次日开盘成交）、日报与回测共用同一个决策函数、券商对账、原子写入、失败即停、盈亏账本核对、中文日报。v2 必须继承这些，不许退化。
2. **v1 经济逻辑冻结**：改造期间 v1 只修日常运行的阻塞点（见 §3.1），不再调任何策略规则，避免两条线同时变动。
3. **先有尺子再动刀**：任何删除或保留模块的决定，都必须来自阶段 3 的评估实验室，而不是在冻结的 34 只样本上比较。

## 4. 阶段 1：数据层重建（P5）

### 4.1 存储模型：原始价格和复权因子分开

```
data/
  raw/daily/<symbol>.csv        不复权 OHLC、preclose、volume(股)、amount(元)、
                                tradestatus、is_st、up_limit、down_limit
  raw/index/<symbol>.csv        不复权指数
  ref/adj_factor/<symbol>.csv   ex_date, factor（只追加）
  ref/corporate_actions.csv     ex_date, symbol, cash_div, bonus_ratio, transfer_ratio, rights…
  ref/securities.csv            symbol, name, list_date, delist_date, board
  ref/st_history.csv            symbol, start, end
  ref/industry_history.csv      symbol, classification, code, start, end
  ref/calendar.csv              交易日历
  MANIFEST.json                 每个文件的 sha256，外加逐日链式前缀哈希
```

要点：

- **原始数据天然只追加**。分红和送转只会在 `adj_factor` 和 `corporate_actions` 中追加新行，不会改写任何已有行，因此"只追加 + 前缀哈希"的机制可以原样保留，P5 的核心冲突自然消失。
- **复权在读取时计算**。特征层使用"截至决策日的前复权"：`adj_close(t) = close(t) × factor(t) / factor(as_of)`。所有基于收益率、均线比值、ATR 比率的特征对复权基准不敏感，这一点要用不变性测试钉住（见 §4.4）。
- **执行和账户一律使用原始价格**：股数、手数、最低佣金、参与率、涨跌停价都按真实价格计算，与券商口径一致。
- 数据源供应商偶尔会修正历史数据。刷新时如果发现已有行被改动，不静默覆盖，而是写入 `data/corrections.jsonl`，由人工确认后生成新快照。

### 4.2 数据源

| 用途 | 候选来源 | 说明 |
|---|---|---|
| 原始日线 + preclose + 停牌 + ST 标记 | baostock `query_history_k_data_plus`（`adjustflag=3`）；AkShare `stock_zh_a_hist(adjust="")` | baostock 免费且覆盖已退市股票，字段含 `preclose/tradestatus/isST` |
| 复权因子 | baostock `query_adjust_factor`；Tushare `adj_factor` | 与现有腾讯数据交叉核对 |
| 涨跌停价 | Tushare `stk_limit`（需要积分），否则按 §5.1 规则计算 | 优先使用官方价格，不自己编码规则 |
| 证券列表（含退市） | baostock `query_stock_basic`；Tushare `stock_basic(list_status='D')` | 点时股票池必须包含退市股 |
| 行业历史 | Tushare `index_member_all`（申万成分的纳入和剔除日期）；AkShare 申万历史分类接口 | 点时股票池的关键输入 |
| 指数 | 腾讯（现有）、baostock、AkShare | 解决"指数不能刷新" |

> 各接口的字段名、单位和覆盖范围，要在本阶段第一步用小样本实测核实后再定稿。表中内容是候选，不是结论。

至少用两个来源交叉校验收盘价和成交量，偏差超过阈值（例如收盘价 0.5%）时拒绝写入并报告。

### 4.3 CLI

```bash
uquant data-update --date 2026-09-25            # 股票 + 指数 + 参考数据，一次完成
uquant data-check  [--since 2023-01-01]         # 内容校验，输出问题清单
uquant data-snapshot --output snapshots/…       # 生成回测用的只读快照与清单
```

`daily` 运行前自动调用 `data-check` 检查当日数据，有阻断级问题就停下。

### 4.4 内容校验（不只是哈希）

| 检查 | 规则 | 能抓到的问题 |
|---|---|---|
| 日历完整性 | 上市到退市之间，每个交易日要么有行情，要么 `tradestatus` 为停牌 | sz000636 两年缺口 |
| OHLC 一致性 | `low ≤ open, close ≤ high`，全部为正 | 脏数据 |
| VWAP 落在区间内 | `amount / volume` 落在 `[low, high]`（允许少量容差） | 前复权价与原始成交额混用、成交量单位（手/股）错误 |
| 涨跌幅合法 | `|close/preclose − 1|` 不超过该日的涨跌停幅度加容差（新股无限制日除外） | 缺少复权、错行 |
| preclose 连续 | 无公司行动时 `preclose(t) = close(t−1)`，有公司行动时与因子一致 | 复权因子缺失 |
| 零成交 / 长期不变价 | 标记为可疑 | 停牌误标 |
| 复权不变性 | 原始价格加因子计算出的日收益，与供应商的复权日收益一致 | 因子错误 |
| 跨源一致 | 两个来源的收盘价和成交量偏差在阈值内 | 单源错误 |

**完成标准**：`data-update` 可以完整刷新全部股票、指数和参考数据；`data-check` 对 `data/frozen` 能报出 sz000636 缺口和 VWAP 越界的行；复权不变性测试通过；除权日之后再刷新，不会触发历史前缀错误。

## 5. 阶段 2：执行模型修正（P6）

### 5.1 涨跌停

优先使用供应商提供的当日 `up_limit/down_limit`。没有时，按板块、ST 状态、上市天数和日期计算：`limit = round(preclose × (1 ± r), 2)`，其中 `r` 取值：

| 情形 | r |
|---|---|
| 沪深主板 | 10% |
| 主板 ST / *ST | 5%（交易所 2025 年调整为 10%，生效日以公告为准，写成带日期的规则表） |
| 创业板（300/301） | 2020-08-24 起 20%，之前 10% |
| 科创板（688/689） | 20% |
| 北交所 | 30% |
| 新股上市初期 | 科创板、创业板（注册制后）前 5 日不设限；主板在全面注册制（2023-04）后前 5 日不设限，之前首日为 +44% / −36% |

判断方式从"开盘价 ≥ 上限 × 0.999"改为**与涨跌停价精确比较**，并单独识别一字板（开盘 = 最高 = 最低 = 涨跌停价）。

### 5.2 费用按日期取值

新增费用表 `fee_schedule`：

| 项目 | 规则 |
|---|---|
| 印花税（仅卖出） | 2023-08-28 之前 0.1%，之后 0.05% |
| 过户费（双向） | 2022-04-29 之前 0.002%，之后 0.001% |
| 佣金 | 按账户设置，最低 5 元 |
| 红利税 | 按持有期差别化：1 个月以内 20%，1 个月到 1 年 10%，超过 1 年免征（回测中用于模拟现金分红） |

### 5.3 股数、容量与滑点

- 股数统一为 `floor(目标金额 / 原始价格 / 100) × 100`；科创板首笔至少 200 股，之后可以按 1 股递增。
- 容量为 `前一日原始成交量(股) × 参与率`，与股数单位一致。**删除 `open_execution.py:233-235` 的单位猜测启发式**，单位由数据层保证。
- 成交额缺失的行由数据层补全，或者标记为不可交易；不在执行层估算。
- 滑点从固定 10 个基点改为 `基础滑点 + k × sqrt(参与率)`，并在评估面板里强制跑一遍"成本 × 2"的压力场景。

### 5.4 回测中的公司行动

在回测账户中模拟现金分红（按 §5.2 扣税后入账）、送股和转增（股数增加、成本摊薄）、配股（默认不参与，按市值损失处理）。这样回测账本和真实券商账本的口径一致，§3.1 里桥接用的 `corporate_actions` 输入格式也可以直接复用。

**完成标准**：执行层单元测试覆盖上面每一种情形；对 `sz300308` 抽查若干笔成交，股数和金额与原始价格口径一致；同一笔订单的容量上限与真实成交量的比例正确。

## 6. 阶段 3：评估实验室（P1）

评估实验室是一个**独立的包 `lab/`**，不进入生产 wheel。它只调用 v1 或 v2 的公开决策函数和执行模拟器。

### 6.1 点时股票池（消除成员偏差）

股票池不再是一份手写名单，而是一条**在每个调仓日只用当日可得信息执行的规则**：

```
universe(t) = { s :
    industry(s, t) ∈ 主题行业代码集合       # 用 industry_history 在 t 当日的归属
    AND listed_days(s, t) ≥ 120
    AND NOT is_st(s, t)
    AND median_amount_60d(s, t) 位于主题内前 N 名 或 ≥ 阈值
}
```

- 主题行业代码（例如 AI 链对应申万二级或三级的通信设备、半导体、元件、光学光电子、计算机设备、IT 服务等）在预登记文件中写死。
- 名单每月按规则重算一次；被剔除的股票如有持仓，按正常退出规则处理，不强制清仓。
- **必须包含后来退市、ST 或长期下跌的股票**；它们在当时满足规则，就应该出现在当时的股票池中。
- 现有 34 只名单保留为"v1 历史参照池"，只用于和 v1 结果对照，不再作为任何门槛的输入。

### 6.2 基准（消除"绝对倍数"的误导）

每个面板单元都要同时运行以下基准，**结果一律以相对基准的超额形式报告**：

| 编号 | 基准 | 作用 |
|---|---|---|
| B0 | 股票池等权，每月再平衡 | 这个池子本身的 beta |
| B1 | 对应的申万行业指数或主题 ETF，买入持有 | 可以直接买到的替代品 |
| B2 | B0 加择时：主题指数高于 MA120 时持有，否则空仓 | 最简单的趋势择时 |
| B3 | 动量前 k 名（k = 3 或 5），每月轮动，带 MA60 过滤 | 最简单的"领涨"策略 |
| B4 | B3 加简单风控：组合回撤超过 15% 时减半仓，回到 MA 上方后恢复 | 最简单的"领涨 + 风控" |

B2 到 B4 每个都不超过 100 行代码。**如果复杂策略跑不赢 B3/B4，这份复杂度就没有正当理由**，这是 §7 决策点 D1 的依据。

### 6.3 指标

- 主指标：相对 B0 的超额年化收益、Calmar、最大回撤比（策略回撤 ÷ B0 回撤）。
- 辅助指标：Sharpe、下行波动、换手、单票盈亏贡献集中度（Top-1 占比）、持仓天数分布。
- **起点网格**：每个月第一个交易日作为起点，分 12 个月和 24 个月两种持有期，报告超额收益的分布（中位数、10% 分位、正超额比例），而不是单一起点的结果。
- **剔除赢家**：每个面板剔除事后涨幅前 1 名和前 3 名，策略和基准在**同一个缩减后的池子**上重跑。

### 6.4 跨主题面板（控制主题选择偏差）

主题选择偏差来自"2026 年才知道 AI 是主线"。唯一的对策是：用同一套引擎、同一套参数，去跑**事先登记、包含牛市和熊市**的其他主题。

| 主题 | 区间 | 性质 |
|---|---|---|
| AI 产业链（点时规则版） | 2023-01 → 最新 | 开发集 |
| 半导体 | 2019-01 → 2023-12 | 开发集（2019–2021 牛市，2022–2023 熊市） |
| 新能源（电池、光伏设备） | 2019-01 → 2024-12 | 验证集（先暴涨后腰斩） |
| 医药 / CXO | 2018-01 → 2023-12 | 验证集（先牛后深熊） |
| 食品饮料 / 白酒 | 2016-01 → 2024-12 | 验证集（长牛后长熊） |
| 计算机 / 传媒 | 2013-01 → 2018-12 | 验证集（2015 年泡沫与崩盘） |
| 券商 | 2014-01 → 2018-12 | 验证集（高 beta 急涨急跌） |
| 有色 / 煤炭 | 2020-01 → 2024-12 | 验证集（周期品） |

- 开发集可以反复使用；**验证集只在里程碑时运行**，每运行一次都记入台账（§8.3），查看次数本身也是需要披露的统计量。
- 主题和区间在阶段 0 写入预登记文件，事后不能增删。
- 回测引擎必须足够快才撑得起这个面板：例如 8 个主题 × 约 100 只股票 × 起点网格 × 剔除赢家，需要几千次回测。以现在每个决策日 0.78 秒（34 只股票）的速度完全跑不动，这也是 §8.5 要求 v2 向量化的直接原因。

**完成标准**：`lab run --panel registered` 可以一键跑完面板，输出每个单元的原始结果、基准结果和汇总报告；点时股票池有测试证明它在 `t` 日不读取 `t` 之后的任何信息；面板结果中出现退市和 ST 股票。

## 7. 阶段 4：诊断 v1 与决策点 D1

数据层和实验室就绪之后、动手写 v2 之前，先用新尺子量一次 v1。做法是由新数据层导出 v1 能读取的前复权 CSV（通过一个适配器），v1 的决策和执行代码一律不动：

1. v1 在 AI 链点时池、起点网格、剔除赢家、跨主题开发集上的结果；
2. 与 B0 到 B4 的对比。

适配器还要解决一个问题：v1 的行业归属来自带哈希锁定的 34 只名单（`REQUIRED_AI_UNIVERSE_SHA256`），不在名单里的股票一律被当作 `unknown` 行业并受 18% 权重上限约束。因此需要一个只在实验室生效的注入入口，用 `industry_history` 生成的点时行业映射替换它；生产路径上的锁定保持不变。

v1 在上百只股票的池子上会很慢（每个决策日的耗时大致随股票数增长），所以诊断只跑开发集中做出 D1 判断所必需的单元，并行分摊到多个进程；不对 v1 跑验证集，免得在 v1 身上消耗验证集的查看次数。

**决策点 D1**：

- **v1 能稳定跑赢 B3/B4**：说明 v1 里确实有价值的成分，v2 前向准入时优先考察 v1 的模块。
- **v1 跑不赢 B3/B4**：说明 v1 的复杂度在点时股票池上没有带来收益。v2 以 B3/B4 为起点，模块准入门槛不变。同时要正视一件事：在点时股票池上，合理的收益预期会远低于 23 倍这个数字。

两种结果都是有效结论，诊断报告应如实记录，不修改门槛。

## 8. 阶段 5：v2 精简内核（P3、P4）

### 8.1 为什么重建，而不是在 v1 上做消融

v1 的 24 种机制通过 85 个持久字段互相牵连（例如战略授冠、epoch、rearm、恢复权、保护权重之间的依赖）。关掉其中一个，很容易让另一个进入从未测试过的状态。现有消融协议本身也规定，没有产生行为分叉的消融只能判为 `INCONCLUSIVE`，无法据此删除模块。因此采用**前向准入**：从最简单的基线出发，一个模块一个模块地往里加，每个模块单独证明自己的价值。

### 8.2 目标架构

```
uquant/                      生产包（目标规模：1–1.5 万行以内）
  data/        读取原始数据和因子、交易日历、点时股票池、内容校验
  features/    向量化特征面板（日期 × 证券），每次回测只计算一次
  signals/     市场状态（机会 / 风险）、证券排序
  portfolio/   目标权重与约束（总仓、单票、持仓数、行业、最小交易）
  execution/   A 股规则模拟（§5）
  account/     现金、批次、订单、成交、峰值、风险状态（目标 ≤ 15 个持久字段）
  broker/      券商快照对账（含公司行动、人工成交）
  report/      日报（沿用现有中文版式）
  cli.py
lab/                         评估实验室（不进入 wheel）
  universes/  benchmarks/  panel/  metrics/  trials/  stats/（PBO、DSR）
```

关键设计原则：

1. **市场状态不靠持久化记忆**。连续确认天数、趋势持续期等，全部由截至当日的价格窗口重新计算，而不是保存在账户里逐日累加。这样，从任何起点回测，只要市场数据相同，同一天就会得出同样的市场判断（只有持仓不同）。这会直接消除 §1.1 那种"起点挪一个月结果减半"的路径依赖，也能省掉大部分回放身份校验机制。
2. **账户只保存必须持久化的事实**：现金、持仓批次、订单、成交、权益峰值，以及少量确实需要记忆的风险状态（例如风险等级及其持续天数）。
3. **决策函数保持纯函数**：`decide(features_row_t, account_state) -> (targets, orders, explanation)`。日报和回测继续共用这一个函数（保留 v1 的核心优势）。
4. **身份校验保持简单**：每次运行输出 `git_sha + data_manifest_sha + config_sha` 三元组即可，取代源码表面注册表、封签等复杂机制。

### 8.3 过拟合控制协议

| 措施 | 规则 |
|---|---|
| 参数预算 | v2 内核的自由数值参数不超过 25 个；窗口类参数优先取 20 / 60 / 120 这类约定俗成的值，不做搜索。评分使用少数因子的**等权秩平均**，不使用手工小数权重 |
| 试验台账 | 每跑一次候选配置，在 `lab/trials.jsonl` 追加一行：配置、代码 SHA、使用的数据集、面板上逐单元的日收益。只追加，不删除 |
| 统计检验 | 在台账上计算 PBO（CSCV 组合对称交叉验证得出的回测过拟合概率）和 Deflated Sharpe Ratio。门槛见 §9 |
| 参数鲁棒性 | 每个参数上下扰动 20%，面板中位 Calmar 不低于名义值的 80%。要的是一片平台，而不是一个尖峰 |
| 禁止按日期修补 | 如果一次改动的动机是某个具体历史事件，就必须证明在**剔除该事件所在月份**之后的面板上仍然有改善，否则不接受 |
| 验证集隔离 | 验证集只在里程碑运行，且运行次数写入台账和报告 |

### 8.4 前向准入流程

1. **起点**：在 B3/B4 中选开发集上表现较好的一个作为 v2 种子，用 v2 的数据、执行和账户层实现。
2. **候选模块池**：从 v1 的 24 种机制中归纳出可以独立开关的模块，按预期价值排序，例如：
   - 风险阶梯（总仓上限随市场和组合回撤变化）
   - 结构退化退出（替代固定 MA 过滤）
   - 盈利加仓（ADD1/ADD2）
   - 替换轮动（带最短持有和轮动预算）
   - 行业集中度与相关簇约束
   - 冲击修复（分阶段恢复仓位）
   - Risk Sentinel 冻结新增
   - 长期主导者持有特例（战略授冠逻辑的简化版）
3. **准入规则**，一个模块一次，全部满足才保留：
   - 开发集面板上，中位超额 Calmar 提升，且配对 bootstrap 检验的单侧 p < 0.1；
   - 10% 分位（最差情形）不恶化；
   - 新增参数计入 25 个的预算；
   - 验证集在里程碑时确认同方向（不要求显著，但不能反向）。
4. **不通过的模块不进入 v2**。v1 中对应的代码随阶段 7 一起删除。

### 8.5 性能目标

- 特征按"日期 × 证券"面板一次性向量化计算，决策时按行读取。
- 目标：34 只股票、3.5 年的回测在 5 秒以内；300 只股票、10 年的回测在 60 秒以内。
- 实现上需要一条"逐日决策与向量化特征等价"的测试：随机抽取若干天，确认逐日从原始数据重算的特征与面板中的值一致，以此保证因果性。

**完成标准**：v2 内核通过全部单元测试和等价测试；参数数量不超过预算；性能达标；台账和统计模块可以运行。

## 9. 阶段 6：新门槛与 CI（P2）

### 9.1 删除的门槛

- `principal_wealth_floor = 15.0` 以及所有"≥ 冠军财富 × 系数"的比较；
- `cross_ai_core_strategy_contract.json` 中的 23.28 倍门槛；
- Strategic Ownership / Grant / Absolute LOO 这类以 v1 内部机制为验收对象的合同（v2 中这些机制可能根本不存在）；
- 单账户 40 笔订单上限（改为换手和成本敏感性检查）。

### 9.2 新门槛（草案，阶段 0 定稿后冻结）

所有门槛都是**相对**的，都在点时股票池上计算：

| 编号 | 门槛 |
|---|---|
| G1 | AI 链点时池全区间：Calmar ≥ max(B0, B2) |
| G2 | 起点网格（12 个月持有期）：相对 B0 的超额中位数 > 0，且正超额比例 ≥ 60% |
| G3 | 剔除事后前 1 名和前 3 名赢家后，在同一个缩减池上 Calmar ≥ B0 |
| G4 | 跨主题验证集：至少三分之二的主题 Calmar > max(B0, B2)；熊市段的最大回撤 ≤ B0 回撤 × 0.7 |
| G5 | 成本 × 2 时 G1 仍然成立 |
| G6 | 参数扰动 ±20%：面板中位 Calmar ≥ 名义值的 80% |
| G7 | 台账上 PBO < 0.3，DSR 显著（概率 ≥ 0.9） |

门槛数值属于用户决策；关键是**在看到验证集结果之前**确定并冻结。之后如果改门槛，只能新开一个版本，并在报告中同时展示新旧两版结果。

### 9.3 CI 分层

| 层级 | 触发 | 内容 | 目标耗时 |
|---|---|---|---|
| 快速层 | 每次推送 / PR | ruff、mypy、单元测试、执行规则测试、一次小样本确定性回测（结果哈希固定） | ≤ 10 分钟 |
| 面板层 | 手动或每晚 | 开发集面板加上 G1–G3、G5、G6 | ≤ 60 分钟（依赖 §8.5 的速度） |
| 里程碑层 | 手动 | 验证集面板加上 G4、G7，结果写入台账 | 单次运行 |

同时删除 `absolute-generalization-acceptance`、`strategic-*-acceptance`、`strategy-generalization`、`strategy-performance` 等工作流，由上面三层替代。
