#### 阶段 0：失败台账与可行性上界（只读，不改策略）

1. **失败台账**：从最新 HEAD 的 CI 原件和已保全 ZIP，逐条记录场景、指标、门槛、实际值、超限幅度、
   类别（绝对硬门 / 相对比较 / 身份 / 工程），以及 **main 在同输入下是否也失败**（复用 main 原件，
   缺失时只对硬门场景补跑 main）。
2. **C3 预算重算**：用 `uquant.validation.ci_artifacts c3-budget` 在已有 192 Economic + 45 Performance
   原始账户上重算，输出旧政策与 C3 预算两种失败数并列；不删除旧失败。
3. **配置身份**：确认 1 项配置身份失败在授权迁移下是否已消除；未消除则补齐迁移记录，不重标历史配置。
4. **可行性上界（关键新增）**：在同一交易池、T+1、涨跌停不可成交、费用滑点、现金多头的合法动作
   集合内判断。注意：剔除场景本身没有财富门槛，单独降暴露总能过 30%；真正的约束是**同一条规则
   作用于全部账户时**，主账户财富门槛和剔除场景回撤硬线能否**同时**满足。
   - **联合暴露前沿**：对全部账户的已有逐日收益 r_t，同时施加同一个常数暴露 λ∈{1.0, 0.95, …, 0.5}，
     以及同一个回撤刹车规则族（触发 b、残余 e 的粗网格，仅用于判断可行性，不用于选参）。
     输出每个设定下的“主账户财富、剔除场景最大回撤、LOO P90 回撤”，找出同时满足
     “主 ≥ 23.284× 且全部回撤 ≤ 28%（留 2pp 余量）”的区域。
   - **短窗事后上界**：对 Performance 失败窗口（如 A/2024、D 急跌），在交易池内用事后信息求简单上界
     （最佳单股、最佳等权组合、全程空仓），判断门槛在该窗口是否可能达到。
   - 判定：可行区域为空、或事后上界也达不到门槛，标记 **STRUCTURALLY_INFEASIBLE**（注明是
     “规则族内不可行”还是“任何策略都不可行”，前者只说明需要更强机制），进入阶段 F；

5. 产出写入 PR #92 描述（一张表加结论），必要原件放入已有证据目录。

每一梯级运行前冻结：假设、机制、参数来源（由阶段 0 上界或既有常量推出）、预期改善场景、反证条件；

| 梯级 | 机制 | 新参数 | 主要针对 |
|---|---|---|---|

原生哨兵集（运行前冻结，不随结果更换）：主连续账户；Ownership 剔除 300308 / 300394 / 300502；

#### 阶段 3：完整验收（只对一个稳定候选）

1. 先完成纯工程修复并单独提交：Economic 连续窗口 7100 秒超时，改为逐场景落盘加断点续跑，

2. 小规模哨兵验证 runner、schema、归因、失败保留和读回后，跑完整 Economic 192、Performance 45、
   Absolute 34 LOO 加 7 组件、Ownership 全分片；同输入与 main 完整对照。
3. 结果绑定真实生产者 SHA，不改贴；不以旧 CI 或部分矩阵冒充新 HEAD 结果。
4. 完整矩阵出现哨兵外的新失败：进入阶段 F，把新失败账户加入哨兵集（只增不减），回到阶段 2。

#### 阶段 F：失败诊断与下一步（决策表）

每次失败先做**逐日资金归因**（哪一段、哪只持仓、哪个决策造成损失或收益丢失），再按下表选择下一步。
同一问题连续两次尝试都没有新的因果证据时，升级到下一行，不在原地反复调参。

| 失败现象 | 诊断 | 下一步 |
|---|---|---|
| 硬线仍超、主财富充足 | 风险预算不足 | 在阶段 1 平台内向更保守一档移动；平台内无解则上一梯级 |
| 硬线过了、主财富跌破 0.90×C3 或 23.284× | 刹车过早或恢复太慢 | 归因到具体刹车 / 恢复事件；改进恢复证据（例如用既有健康恢复条件更早再入场），不放松触发条件 |
| 订单 / 费用超标 | 刹车在阈值附近反复触发 | 加迟滞（再入场条件与触发条件分离，复用既有状态），不加等待期 |
| 预筛与原生偏差 > 2pp | 路径依赖大 | 该梯级只用原生回放筛选，缩小候选数 |
| 完整矩阵新失败 | 哨兵代表性不足 | 加入哨兵集，回阶段 2 |
| 阶段 0 判定 STRUCTURALLY_INFEASIBLE | 门槛在合法动作集合内不可达 | 走下方“不可达分支” |
| L1–L5 全部未达标，但阶段 0 判定可行 | 机制空间不够 | 以事后上界与候选的差异归因（入场时机 / 退出时机 / owner 选择 / 仓位）为依据，设计一个新机制作为 L6，并满足第三节原则；最多扩展 2 个新梯级 |

**不可达分支**：不得自行改门槛。准备一份 ADR 草案（放在 `docs/decisions/`，状态 Proposed），内容包括：
上界计算方法和原件、“即使事后最优也无法满足”的证明、该门槛的合同来源、可选修正方案
（例如改为相对 main 的不退化，或按场景可达上界定义），以及每种方案的影响。交给用户决定；
**等待用户决定期间继续推进其余可行的门槛**，不停工。
